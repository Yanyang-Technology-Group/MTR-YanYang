Target: Minecraft 1.20.1 Fabric, MTR 4.0.5. All work was performed without
subagent delegation. The bundled TSC binary remains unchanged.

## Baseline

A 40-second JFR profile was recorded from the user's running client on a
Ryzen 5 5500 and RX 6700 XT, with Sodium 0.5.13, Iris 1.7.6, shaders disabled
and render distance 12. The client had the first performance build installed.

The InitClient platform lookup wrapper had 316 samples, but includes the

call stacks and measured GC pauses, not an FPS measurement or a CPU/GPU split.

## Changes

- Increase the bounded platform query cache from 1,024 to 32,768 entries.
  Every route-map block performs a separate query; sequential scans above
  the old capacity evicted the entire previous frame. Static sync still
  invalidates results, including cached misses.
- Track only resources with loaded data for expiry and remove expired entries.
  Unloaded model definitions no longer participate in every client tick.
  Weak ownership, hit renewal and recursive loading behavior are preserved.
- Cache Iris's resolved order at its sort-and-reset boundary. Compare every
  vertex identity, vertex/edge iteration order, edge weight and category
  boundary; changed inputs use Iris's original algorithm. Snapshots are limited
  to 65,536 records. Unknown graph implementations and oversized inputs bypass
  caching. Returned lists are independent because Iris mutates them.

## Verification

All 35 Fabric tests passed and the Fabric 1.20.1 release build succeeded with
JDK 21 running Gradle and Java 17 as the mod compilation target.

Regression coverage includes 3,000 platform queries across three frames,
10,000 unloaded resources, repeated cyclic graphs, changed weights/edges/order,
resource replacement with equal but distinct objects, mutable returned lists,
and oversized/unknown graph fallback.

A real client smoke check with Iris 1.7.6 and Sodium 0.5.13 on Java 17 exercised

The user's running game was not restarted or modified. Post-change frame times
and cache hit rate in the actual station still require testing the new JAR in
the same scene. No graphics-quality reduction or GC flag change was applied.

## Third Build: Iris Ordering

The previous one-entry cache recomputed both graphs on every call in a test
alternating 100 world and minimap passes. This demonstrates an invalidation
mechanism, not the actual station's cache hit rate. JourneyMap's minimap was
also observed calling the same Iris buffering path.

- Retain up to eight complete graph orders using LRU eviction. Each snapshot
  is limited to 65,536 records and retained snapshots to 262,144 records total.
- Reuse feedback-edge results for unchanged strongly connected components
  inside Iris's existing algorithm. This preserves stable cyclic groups when
  other groups, transparency categories, or acyclic edges change. Keep at most
  64 component results and 131,072 snapshot records in total.
- Snapshot the original input before the solver removes edges. Preserve vertex
  and edge iteration order, layer identity, weights and category boundaries.
  Hashes only filter candidates; exact comparisons decide every cache hit.
- Check component weights against the parent graph and include solver identity
  in the component key. Unknown weight implementations and differing parent
  weights bypass caching. The original cycle solver, SCC decomposition and
  topological sort remain responsible for misses and changed inputs.
- Scope the optional library hook to an Iris sorting call on its current
  thread. Nested calls restore the previous scope; exceptions clear it.
  Cached feedback graphs are only read by Iris; returned complete order lists
  remain caller-owned. No graphics settings or simulation rates change.

All 44 Fabric tests passed and the 1.20.1 Fabric release build succeeded.
New regression coverage includes alternating passes, LRU count/record limits,
parent-weight changes, unchanged components, fingerprint collisions, nested
calls, failure cleanup and unknown input fallback.

An isolated Java 17 client with Iris 1.7.6 and Sodium 0.5.13 exercised the actual
Mixin hook and original solver. The constructed workload had two cyclic groups
of 90 layers with 720 cycle edges total, plus an acyclic edge whose weight
changed every frame. A minimap-like empty pass followed every world pass.
Across 40 frames, the original solver ran 80 times and the component cache ran
it twice. All 40 output lists matched the original ordering. Changing one
cyclic group caused exactly one additional solve and again matched Iris.

After 20 warmup frames, the next 20 frames averaged 45.568 ms for original
ordering and 0.518 ms with caching. These timings exclude input construction
and describe this synthetic workload only; they do not establish an FPS gain
in the user's station. A separate isolated run without Iris passed and exited
normally. Smoke helpers are excluded from the release artifact.

### Changes

- Add conservative camera-frustum checks for the built-in PSD/APG/lift doors
  and PSD/APG route-map renderers, which otherwise enter Sodium's global block
  entity path. Door bounds include two blocks of padding around the source
  block, covering the full travel and end panels; route maps use one block.
  Door animation ticks before visibility rejection. Unknown renderer subclasses
  retain their existing behavior. Shadow rendering, missing frustums and world
  mismatches bypass culling. Fabric START/AFTER_SETUP/END events manage a
  render-thread-local frame context.
- Replace MainRenderer's linear material maps with insertion-ordered hash maps.
  Swap pending/current frame maps instead of copying every material entry.
  Preserve material, layer, priority and callback order, next-frame submissions,
  and cancellation. Reuse the untextured identifier and render-layer array.
- Construct each lift's procedural ModelLift1 once in its existing LiftWrapper.
  Rebuild when rounded dimensions or double-sided configuration change; dynamic
  network updates with unchanged geometry retain the model. Wrapper removal
  releases its model, and each lift owns a separate instance.
- Precompute the finite door texture identifiers and read the door block state
  once per visible render instead of formatting paths and querying it repeatedly.

## Fifth Build: Moving Outside the Station

The user reports stable 60+ FPS on the platform level with performance4, but
roughly 20-29 FPS while moving outside with multiple platforms in view. The
installed performance4 artifact's SHA-256 was verified before a new 45-second
JFR recording. Only the JVM's built-in recording facility was attached.

Of 1,795 render-thread samples, 467 (26.0%) include the Iris feedback cycle
solver, 415 (23.1%) include complete ordering, 198 (11.0%) include model-part
rendering, and 56 (3.1%) include route-map span queries. These are overlapping
stack samples, not exclusive frame times. HashMap tree lookup was the top leaf
frame (168 samples). There were 10 GCs, 93.092 ms total pauses, and 17.869 ms as
the longest pause. Recording: `build/performance/mtr-outside-v4.jfr`.

### Changed Cycle Components

The original solver repeatedly traverses up to eleven graph variants, using
vertex objects in hash maps and sets. Stable-component caching cannot avoid
this work when a component changes. The new path temporarily labels its
vertices with consecutive integers and invokes the same Iris solver. It then
restores the original objects in the returned feedback graph. Vertex and edge
iteration order, weights, random traversal permutations, candidate count and
tie-breaking remain unchanged. This removes repeated expensive/colliding
material-object hashes from the inner search without approximating the order.

- Keep existing full-graph and component caches; relabel only component misses.
- Restrict relabeling to the exact SimpleFeedbackArcSetProvider and MapDigraph
  classes within the active Iris ordering scope. Custom providers bypass it.
- Preserve parent weights by checking their equality on every component edge.
  Unknown weights, missing targets, non-identical vertex aliases, components
  smaller than 16 vertices, and inputs over 65,536 vertex/edge records fall back.
- Construct temporary graphs through the optional library's public constructor;
  map access and edge-count updates use the existing optional accessor mixin.
  The original input graph is never changed by relabeling. No Iris dependency
  is bundled, and no shader or graphics options are modified.

### Validation

The isolated Java 17 / Iris 1.7.6 / Sodium 0.5.13 test first reproduced 1,755,135
vertex hash calls for one changing 96-vertex component. After relabeling, all
16 changed graphs returned identical ordered feedback graphs. In the final
run, eight warmed original solves averaged 470.523 ms, versus 26.441 ms through
the new path; vertex hash calls over those eight solves fell from 14,005,272 to
28,848. This deliberately collision-heavy synthetic workload demonstrates the
mechanism, not the speedup expected in the user's world.

An additional 80 randomized changing inputs across every transparency category
produced exactly the same complete render lists as Iris's original provider.
Existing component reuse, shader reload and station rendering checks passed.
Unit tests cover ordered relabeling/restoration, object identity, parent-weight
validation, missing aliases, record limits and outside-scope fallback.

All 54 tests and the Fabric 1.20.1 release build passed. A separate isolated
Java 17 client without Iris also passed after the test fixture's direct Iris
references were moved into a lazily loaded nested class; smoke helpers are
excluded from the release artifact. The fifth build's real-world FPS and p99
frame time require restarting into the new artifact and measuring
the same outside view. Route geometry submission and model vertex work remain
separate costs and were not changed by this build.

## Sixth Build: Repeated Graph Traversal and Station Spans

The user reports only a small outside-station improvement on performance5.
The installed artifact's SHA-256 was verified, and another 45-second JFR
recording was collected using the standard JVM recorder only. Recording:
`build/performance/mtr-outside-v5.jfr`.

Of 1,754 render-thread samples, 354 (20.2%) include the Iris cycle solver,
306 (17.4%) include graph DFS, 290 (16.5%) include model-part rendering,
176 (10.0%) include lift rendering and 75 (4.3%) include station span queries.
These are overlapping sampled stacks, not exclusive timings. Of 342 stacks
including IndexedFeedbackGraph.solve, 340 were in the numbered-graph call to
the original solver: the fifth build was active, but still paid for repeated
adjacency lookups, tree-map comparisons and recursive traversal. GC recorded
12 collections, 93.974 ms total pause time and a 9.513 ms longest pause.

The MTR worker thread had 3,423 sampled stacks inside its tick, dominated by
rail/vehicle ray tracing. A proposed extra opacity cache was tested against
the real occlusion library and discarded: both paths performed the same
4,543 voxel reads because that library already caches them. This build instead
reuses a worker-owned mutable block position and accesses the same native
world/state API, removing per-query mapping wrappers and position allocations.
The existing ray-tracing behavior and scheduling remain in place.

### Changes

- During each supported, numbered Iris component solve, snapshot the original
  graph and its shuffled variants' adjacency lists once. Reuse primitive arrays
  for iterative DFS, matching the original discovery and postorder. The existing
  library still generates candidates, scores weights, resolves ties, chooses
  feedback edges and performs the final topological sort. No candidate or
  iteration count is reduced. Limit snapshots to 12 graphs and 262,144 records
  per solve, with at most 65,536 vertices per graph; unsupported inputs fall back.
  Nested solver scopes restore the previous context and exceptions release it.
- Share directional suffix distances for built-in PSD/APG route-map span
  queries within one world-render frame. Keep renderer/search-side and physical
  direction keys separate; preserve block/end boundaries and the original path
  for extension renderers, shadow passes and missing frame contexts. Each new
  frame/world context discards the previous results, so edits and chunk changes
  are reflected on the next frame. Retention is capped per direction while
  longer runs are still evaluated completely.
- Reuse the worker's BlockPos.Mutable during native opacity checks. Initialize
  its culling instance even when the initial render distance is zero.

An isolated Java 17 client with Iris 1.7.6 and Sodium 0.5.13 passed all existing

## Seventh Build: Allocation Follow-Up

The user reports about 45 FPS outside with performance6 and asks to prioritize
GC pauses. The origins now point to Yanyang-Technology-Group/MTR-YanYang and
Yanyang-Technology-Group/Transport-Simulation-Core respectively. Reviewed MTR
commit 8d4685153e149afdaa3c5a57d383b6c830065eac and TSC commit
d1ae44038c19d37277be754c446135f4741bbfca. Neither commit was merged or copied.

The MTR commit scalarizes rail camera culling. The TSC commit adds a separate
renderScalar entry point but leaves render using the old implementation. The
MTR commit does not call renderScalar. Furthermore, the fork's rail callback
has 13 parameters while this 1.20.1 build uses the bundled 10-parameter API.
These changes therefore cannot simply be combined into the current build.

### Observed Allocations

Built-in JFR recorded 45 seconds in the running performance6 client:
`build/performance/mtr-gc-v6.jfr`. ThreadAllocationStatistics counter deltas
over 44.88 seconds show 164.26 MiB/s on the render thread. Sampled allocation
weights were not divided by duration to estimate allocation rates because
they include extreme outliers. Sample counts also differ by thread sampling
rate and are not a cross-thread allocation ranking.

There were five G1 young collections, 36.928 ms total pause time and 9.077 ms
maximum pause. Post-GC used heap stayed around 2471-2487 MiB; this window did
not demonstrate a full-GC stall or continuing heap growth. It does not exclude
longer pauses outside this capture.

The render-thread stacks show repeated PathData.getHexId formatting during
vehicle signal updates and the traffic addon, plus MSD catenary callbacks,
BlockPos construction, and MainRenderer callback-array growth. MSD catenary
vertex submission also occupies 567 of 1604 render-thread CPU samples. That
CPU work is distinct from GC pauses and is not changed in this build.

### Implementation

- Cache each PathData's two directional IDs lazily. Its endpoints and their
  coordinates are final, including across updateData. Cache misses still
  invoke the original formatter, preserving negative coordinates, ordering
  and ID text. Each cache dies with its path, and there is no global ID map.
- Recycle callback-list backing arrays when the completed frame is released.
  Clear every callback reference before pooling. Keep pending and current
  frames separate, and retain material insertion order. Pool limits are 256
  lists, 65,536 slots per list and 262,144 slots in total; oversized arrays
  are discarded. This reduces buffer growth, not the creation of addon
  callbacks themselves.

Regression tests cover directional cache independence, original formatting,
callback reference cleanup, frame separation, reuse, cancellation, order and
capacity bounds.

### Validation

All 65 Fabric tests passed, and the Fabric 1.20.1 release build completed.
The tests first reproduced the missing cache and finished-frame callback
retention before implementation. A generic-array cast issue found in the
pool tests was fixed before the final full-suite run.

Two isolated Java 17 clients verified the woven PathData implementation.
Across 128 paths, both directions, copied paths, JSON decoding and updates,

The Iris 1.7.6 / Sodium 0.5.13 client also passed the existing complete-order

## Eighth Build: Occlusion Safepoint Responsiveness

The user's remaining symptom is a visible pause while moving the camera. A
built-in JFR capture of the running Java 17 client found that G1 collection
itself was short (longest pause about 14 ms), while safepoint synchronization
occasionally waited about 223 ms. HotSpot's safepoint log identified MTR's
`Thread-12` as the thread still running in the shaded occlusion culling
`isAABBVisible` loop. The delay grows when large station and rail AABBs are
examined; it is a global JVM pause delay, rather than a long GC marking phase.

`OcclusionSafepointMixin` adds a counter-only cooperative poll to the shaded
occlusion scanner's cache and face loops. Every 65,536 visits it performs a
`Thread.yield()` native transition, giving HotSpot a bounded opportunity to
observe a pending safepoint. It does not allocate, change the provider calls,
alter visibility results, or change the culling reach.

### Validation

The Fabric 1.20.1 tests and release build passed. A Java 17 oracle compared 512
random boxes, cache resets, visibility results, and ordered provider calls
between the unmodified and woven implementations. In the large-box stress
case, original safepoint waits were 177 ms median and 185 ms maximum; the
woven implementation measured 0.146 ms median and 0.274 ms maximum. The
cooperative check adds some background culling cost (the stress fixture ran
about 4.3 versus 5.0 calls per second), so the interval is intentionally
infrequent and should be checked against the real world after restart.

The Iris 1.7.6 / Sodium 0.5.13 Java 17 smoke client passed the occlusion oracle,
PathData allocation check, station geometry checks, Iris order oracles and
shader lifecycle checks. The packaged artifact is
`MTR-fabric-4.0.5+1.20.1-performance8.jar`.
